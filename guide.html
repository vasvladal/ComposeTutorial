Jetpack Compose — Beginner's Guide

A walkthrough of the ComposeTutorial Android Studio project: what every file does, and how the Jetpack Compose framework underneath it actually works.

Who this is for — you know some Kotlin, you've opened Android Studio before, and you want to understand Compose from first principles rather than copy-pasting snippets.

Jetpack Compose is Android's modern, declarative UI toolkit. Instead of imperatively mutating XML views (findViewById, view.text = "..."), you describe what the UI should look like for a given state, and Compose figures out how to update the screen when that state changes.

Opening the project

  1. Install Android Studio (a recent stable release) if you haven't already.
  2. File → Open… and select the unzipped ComposeTutorial folder.
  3. Wait for the Gradle sync to finish — Android Studio downloads the dependencies listed in the Gradle files (covered below).
  4. Select the app run configuration and press Run on an emulator or a connected device (minimum Android 7.0 / API 24).
No emulator handy? Every screen in this project also has a @Preview, so you can inspect and iterate on the UI directly in Android Studio's Design pane — see Previews.

Project structure

Here's the full layout of the tutorial project. Everything under app/src/main/java/…/composetutorial is Kotlin/Compose code; everything under res/ is classic Android resources (there are very few of these, because Compose replaces most of what XML layouts used to do).

ComposeTutorial/ ├── settings.gradle.kts ├── build.gradle.kts (project-level) ├── gradle.properties ├── gradle/ │ ├── libs.versions.toml (version catalog) │ └── wrapper/gradle-wrapper.properties └── app/ ├── build.gradle.kts (module-level) ├── proguard-rules.pro └── src/main/ ├── AndroidManifest.xml ├── res/values/ │ ├── strings.xml │ └── styles.xml (minimal launch theme only) └── java/com/example/composetutorial/ ├── MainActivity.kt ├── ui/theme/ │ ├── Color.kt │ ├── Type.kt │ └── Theme.kt └── components/ ├── GreetingCard.kt ├── CounterButton.kt ├── ProfileForm.kt └── TaskList.kt

gradle/libs.versions.toml

/gradle/libs.versions.toml

This is Gradle's version catalog — a single TOML file that centralizes every plugin and dependency version used anywhere in the project. Instead of a version number being hardcoded on some random line of a module's build.gradle.kts, it's declared once here and referenced everywhere else by name. It has three tables:

[versions]
agp = "8.7.0"
kotlin = "2.3.10"
composeBom = "2026.06.00"
# ...

[libraries]
androidx-core-ktx = { group = "androidx.core", name = "core-ktx", version.ref = "coreKtx" }
androidx-compose-bom = { group = "androidx.compose", name = "compose-bom", version.ref = "composeBom" }
androidx-material3 = { group = "androidx.compose.material3", name = "material3" }
# ...

[plugins]
android-application = { id = "com.android.application", version.ref = "agp" }
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
compose-compiler = { id = "org.jetbrains.kotlin.plugin.compose", version.ref = "kotlin" }
  • [versions] — every raw version string, named once.
  • [libraries] — each dependency's Maven coordinates (group + name), pointing at a version above via version.ref. Notice the Compose libraries below the BOM (androidx-material3, androidx-ui, …) don't declare a version at all — the BOM still supplies it at build time.
  • [plugins] — the same idea for Gradle plugins.

Because the file lives at gradle/libs.versions.toml, Gradle auto-detects it and generates a type-safe libs accessor you can use directly in any build.gradle.kts — libs.androidx.material3, libs.plugins.kotlin.android, and so on, with autocomplete in Android Studio.

Why bother? In a project with more than one module, every module used to repeat (and could drift on) its own version numbers. With a catalog, bumping Kotlin or the Compose BOM is a one-line change in this file that every module picks up.

Root build.gradle.kts

/build.gradle.kts

The top-level Gradle file. It doesn't build anything itself — it just declares, with apply false, which plugins are available to sub-modules, so every module in a multi-module project stays on the same version. Each plugin is referenced from the version catalog via alias(libs.plugins.…) rather than a hardcoded id/version pair:

plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.kotlin.android) apply false
    alias(libs.plugins.compose.compiler) apply false
}

Three plugins matter here: the Android Gradle Plugin (knows how to build APKs), the Kotlin Android plugin (compiles Kotlin for Android), and the Compose Compiler plugin — a separate Kotlin compiler plugin that turns your @Composable functions into code Compose can actually run and recompose efficiently.

app/build.gradle.kts

/app/build.gradle.kts

This is where the actual app module is configured: SDK versions, and every library dependency.

The android { } block

SettingMeaning
compileSdkThe Android API version your code is compiled against (gives you access to the newest APIs).
minSdkThe oldest Android version the app will install on.
targetSdkThe API level your app is tested against; affects some runtime behaviors.
buildFeatures { compose = true }Turns on Compose support for this module.

Plugins & dependencies via the version catalog

Rather than writing plugin ids or Maven coordinates by hand, this file pulls everything from gradle/libs.versions.toml through the generated libs accessor:

plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
    alias(libs.plugins.compose.compiler)
}

dependencies {
    implementation(libs.androidx.core.ktx)
    implementation(libs.androidx.activity.compose)
    implementation(libs.androidx.material3)
    // ...
}

The Compose BOM

Compose ships as dozens of separate libraries (ui, material3, foundation, animation, etc.) that all need to be version-compatible with each other. Rather than pinning a version on every single line, you import one Bill of Materials (BOM) platform dependency — itself resolved from the catalog — and every other Compose implementation(...) line below it automatically resolves to a matching, tested version:

val composeBom = platform(libs.androidx.compose.bom)
implementation(composeBom)

implementation(libs.androidx.ui)
implementation(libs.androidx.material3)
Notice neither libs.androidx.ui nor libs.androidx.material3 carries its own version in the catalog — the BOM supplies it at build time.

settings.gradle.kts

/settings.gradle.kts

Declares the name of the whole project and which modules belong to it (here, just :app), plus which repositories Gradle is allowed to fetch dependencies from (Google's and Maven Central).

AndroidManifest.xml

/app/src/main/AndroidManifest.xml

Even a Compose-only app still needs a manifest — it's how Android knows the app exists, what its entry point is, and what it's allowed to do. In this tutorial it declares exactly one <activity>, MainActivity, marked as the launcher activity via the MAIN/LAUNCHER intent filter — i.e. the screen that opens when the user taps the app icon.

In a full app you'd also list permissions here (camera, internet, location...) and any additional activities or services. This tutorial needs none of those.

MainActivity.kt

/app/src/main/java/com/example/composetutorial/MainActivity.kt

The single Activity that hosts the entire UI — a common pattern in Compose apps, since screens are composed and swapped in Kotlin rather than by launching new Activities.

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            ComposeTutorialTheme {
                TutorialApp()
            }
        }
    }
}

setContent { … } is the bridge between the classic Android Activity world and Compose: everything inside it is composable code. There's no XML layout file and no R.layout.activity_main anywhere.

Below the Activity, TutorialApp() is the composable that actually lays out the screen. It wraps everything in a Scaffold (a Material structural component that reserves space for a top bar, and correctly insets your content around it), then stacks the four demo sections — GreetingCard, CounterButton, ProfileForm, TaskList — inside a scrollable Column.

ui/theme/ files

/app/src/main/java/com/example/composetutorial/ui/theme/

Three small files that together define the app's visual identity through Material 3's theming system.

Color.kt

Raw Color(0x…) constants for a light and a dark palette — just values, no logic.

Type.kt

A Typography object overriding a few of Material 3's named text styles (bodyLarge, titleLarge, labelSmall) with this app's font sizes and weights.

Theme.kt

Defines ComposeTutorialTheme, a composable wrapper you call once at the root of the app. It picks a light or dark ColorScheme (respecting the system setting, and even Android 12+'s wallpaper-based "dynamic color" if available), then hands colors + typography to Compose's MaterialTheme:

MaterialTheme(
    colorScheme = colorScheme,
    typography = AppTypography,
    content = content
)

Every composable inside content can now read MaterialTheme.colorScheme.primary, MaterialTheme.typography.bodyLarge, etc., instead of hardcoding colors and fonts.

components/ files

/app/src/main/java/com/example/composetutorial/components/

Four small, focused composables, each demonstrating one core Compose idea. MainActivity.kt assembles all four into one screen.

GreetingCard.kt

Idea: a stateless composable. It takes a name parameter in and emits a Material Card with two lines of text — nothing else. It owns no state and has no side effects, which makes it trivial to reuse and to preview with different inputs.

CounterButton.kt

Idea: state and recomposition. Holds a counter with remember { mutableIntStateOf(0) }. Tapping the button increments it; because the composable reads that state, Compose automatically re-invokes (recomposes) just this small piece of UI whenever it changes.

ProfileForm.kt

Idea: state hoisting. A text field whose current value is stored in a remember { mutableStateOf("") } outside the OutlinedTextField itself, then passed back in via value / onValueChange. The text field doesn't manage its own state — the caller does — which is the standard, testable pattern for interactive Compose UI.

TaskList.kt

Idea: efficient lists. Uses LazyColumn (Compose's equivalent of RecyclerView) backed by a mutableStateListOf of a small Task data class, so only the items currently on screen are composed, and toggling a checkbox updates just that row.

What Jetpack Compose is

Jetpack Compose is Google's modern UI toolkit for Android, built entirely in Kotlin. It replaces the old View system (XML layouts + Activity/Fragment glue code) with a declarative model borrowed from frameworks like React and Flutter:

Classic Views (imperative)Compose (declarative)
How you build UIXML layout files + Kotlin/Java code that mutates viewsKotlin functions that describe UI for the current state
Updating the UIYou manually call setText(), setVisibility(), etc.You change state; Compose re-runs the relevant function(s) automatically
ReuseCustom View subclasses, <include>Plain Kotlin functions

Because UI is just a function of state, most Compose bugs collapse into a much smaller, more familiar problem: "is my state correct?" — rather than "did I forget to update this one view?"

Composable functions

A composable function is any function annotated @Composable. It describes a piece of UI by calling other composables:

@Composable
fun GreetingCard(name: String, modifier: Modifier = Modifier) {
    Card(modifier = modifier) {
        Text("Hello, $name")
    }
}
  • Composable functions can be called only from other composable functions (or from an entry point like setContent { }).
  • They can run in any order, in parallel, and more than once — so they should avoid side effects and just describe UI from their inputs.
  • By convention they take a trailing modifier: Modifier = Modifier parameter (see Modifiers) so the caller controls layout.

State & recomposition

Recomposition is the process of re-running composable functions when the state they read changes, so the UI on screen stays in sync with app state. The key building block is mutableStateOf:

var count by remember { mutableIntStateOf(0) }

Button(onClick = { count++ }) { Text("Tap me") }
Text("Clicked $count times")   // re-runs whenever count changes
  • mutableStateOf (and the specialized mutableIntStateOf, mutableStateListOf, etc.) creates observable state — Compose tracks every composable that reads it.
  • remember { … } caches that state across recompositions of the same composable instance — without it, the state would reset to its initial value every time the function re-ran.
  • remember does not survive configuration changes (like a screen rotation) or process death — for that you'd use rememberSaveable instead.
Smart recomposition: Compose only re-runs the composables that actually read the changed state, not the whole screen — which is why UI stays fast even in large apps.

Modifiers

A Modifier is a chainable set of instructions that decorate or configure how a composable is measured, laid out, drawn, or reacts to input — padding, size, click handling, background color, and more:

Text(
    text = "Hello",
    modifier = Modifier
        .fillMaxWidth()
        .padding(16.dp)
        .background(Color.LightGray)
        .clickable { /* ... */ }
)

Order matters — each modifier wraps the result of the one before it, so padding().background() paints the background outside the padding, while background().padding() paints it inside. Every layout composable in this project accepts an optional modifier parameter for exactly this reason: it lets the parent control spacing and sizing without the child needing to know about its context.

Layouts: Column, Row, Box

Compose has three foundational layout composables, roughly parallel to LinearLayout and FrameLayout in the old View system:

ComposableArranges children…
Columnvertically, top to bottom
Rowhorizontally, left to right
Boxstacked on top of each other (for overlays, badges, etc.)

All three accept Arrangement (spacing between children) and Alignment (how children align on the cross-axis) parameters. MainActivity.kt uses a Column with Arrangement.spacedBy(4.dp) to lay out the tutorial's sections, and TaskList.kt's row uses Alignment.CenterVertically to align a checkbox with its label.

Lists: LazyColumn

For lists that can be long or unbounded, use LazyColumn (or LazyRow) instead of a Column with a loop. "Lazy" means it only composes and measures the items that are actually visible on screen, recycling composables as the user scrolls — the direct analogue of RecyclerView.

LazyColumn {
    items(tasks) { task ->
        TaskRow(task = task, onToggle = { /* ... */ })
    }
}
Using a plain Column for a large or growing list composes every item up front, which wastes memory and CPU. LazyColumn is the correct default whenever the list size isn't small and fixed.

Material 3 components

The androidx.compose.material3 library provides ready-made, theme-aware UI components implementing Google's Material Design 3 spec. This project uses:

ComponentUsed for
ScaffoldTop-level screen structure (top bar, content insets)
TopAppBarThe title bar at the top of the screen
CardAn elevated surface for grouped content
ButtonA clickable, filled call-to-action
OutlinedTextFieldSingle-line text input
CheckboxBoolean toggle inside each task row

Every one of these automatically picks up colors from MaterialTheme.colorScheme and text styles from MaterialTheme.typography — which is exactly what Theme.kt configures.

Theming

Compose theming flows one direction: you set it once, near the root (ComposeTutorialTheme { … } in MainActivity), and every composable underneath reads from it via MaterialTheme.colorScheme / MaterialTheme.typography / MaterialTheme.shapes. This is why none of the four component files hardcode a single color or font — they all defer to the theme, so switching to dark mode, or restyling the whole app, means editing Theme.kt and Color.kt in one place rather than hunting through every screen.

Previews

Any composable annotated @Preview can be rendered by Android Studio's Design pane without building or running the app — no emulator, no device, often in under a second. Every file in components/ ends with one:

@Preview(showBackground = true)
@Composable
private fun GreetingCardPreview() {
    ComposeTutorialTheme {
        GreetingCard(name = "Jetpack Compose")
    }
}

Wrapping the preview in the app's theme (as shown above) ensures it looks exactly as it will at runtime. You can stack multiple @Preview annotations on one function to preview it in light/dark mode, different font scales, or different device sizes side by side.

Try it yourself

  1. Add a fifth section to TutorialApp() using a new composable you write from scratch — start with something stateless, like GreetingCard.
  2. Give CounterButton a "Reset" button that sets count back to 0.
  3. Add a delete icon to each TaskRow in TaskList.kt that removes it from the mutableStateListOf.
  4. Change PurpleLight in Color.kt to a different hue and watch every themed component update.
  5. Add a second @Preview(uiMode = android.content.res.Configuration.UI_MODE_NIGHT_YES) to a component to preview it in dark mode.
