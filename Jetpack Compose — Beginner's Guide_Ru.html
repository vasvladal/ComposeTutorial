Jetpack Compose — Руководство для начинающих

Разбор проекта ComposeTutorial в Android Studio: что делает каждый файл и как на самом деле работает фреймворк Jetpack Compose, лежащий в его основе.

Для кого это — вы немного знаете Kotlin, уже открывали Android Studio и хотите понять Compose с самых основ, а не копировать готовые фрагменты кода.

Jetpack Compose — это современный декларативный UI-инструментарий Android. Вместо императивного изменения XML-представлений (findViewById, view.text = "...") вы описываете, как должен выглядеть интерфейс при заданном состоянии, а Compose сам решает, как обновить экран при изменении этого состояния.

Открытие проекта

  1. Установите Android Studio (свежую стабильную версию), если ещё не сделали этого.
  2. File → Open… и выберите распакованную папку ComposeTutorial.
  3. Дождитесь окончания синхронизации Gradle — Android Studio скачает зависимости, перечисленные в файлах Gradle (о них ниже).
  4. Выберите конфигурацию запуска app и нажмите Run на эмуляторе или подключённом устройстве (минимум Android 7.0 / API 24).
Нет эмулятора под рукой? У каждого экрана в этом проекте есть @Preview, поэтому вы можете просматривать и дорабатывать интерфейс прямо в панели Design в Android Studio — см. Превью.

gradle/libs.versions.toml

/gradle/libs.versions.toml

Это каталог версий Gradle — единый TOML-файл, который централизует все версии плагинов и зависимостей, используемых где-либо в проекте. Вместо того чтобы номер версии был жёстко прописан на случайной строке в build.gradle.kts какого-то модуля, он объявляется один раз здесь и везде далее упоминается по имени. В нём три таблицы:

[versions]
agp = "9.4.1"
kotlin = "2.4.20"
composeBom = "2026.09.00"
# ...

[libraries]
androidx-core-ktx = { group = "androidx.core", name = "core-ktx", version.ref = "coreKtx" }
androidx-compose-bom = { group = "androidx.compose", name = "compose-bom", version.ref = "composeBom" }
androidx-material3 = { group = "androidx.compose.material3", name = "material3" }
# ...

[plugins]
android-application = { id = "com.android.application", version.ref = "agp" }
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
kotlin-compose = { id = "org.jetbrains.kotlin.plugin.compose", version.ref = "kotlin" }
  • [versions] — каждая «сырая» строка версии, названная один раз.
  • [libraries] — Maven-координаты каждой зависимости (group + name), ссылающиеся на версию выше через version.ref. Обратите внимание: библиотеки Compose под BOM (androidx-material3, androidx-ui, …) вообще не объявляют версию — её по-прежнему подставляет BOM во время сборки.
  • [plugins] — та же идея для плагинов Gradle.

Поскольку файл лежит в gradle/libs.versions.toml, Gradle автоматически его обнаруживает и генерирует типобезопасный аксессор libs, который можно использовать напрямую в любом build.gradle.kts — libs.androidx.material3, libs.plugins.kotlin.android и так далее, с автодополнением в Android Studio.

Зачем это нужно? В проекте с более чем одним модулем каждый модуль раньше повторял (и мог разойтись по) свои номера версий. С каталогом обновление Kotlin или Compose BOM — это изменение одной строки в этом файле, которое подхватывают все модули.

Корневой build.gradle.kts

/build.gradle.kts

Верхнеуровневый файл Gradle. Он сам ничего не собирает — он лишь объявляет с apply false, какие плагины доступны подмодулям, чтобы каждый модуль в многомодульном проекте оставался на одной версии. Каждый плагин берётся из каталога версий через alias(libs.plugins.…), а не через жёстко прописанную пару id/версия:

plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.kotlin.compose) apply false
    
}

Здесь важны три плагина: Android Gradle Plugin (умеет собирать APK), плагин Kotlin Android (компилирует Kotlin под Android) и плагин Compose Compiler — отдельный плагин компилятора Kotlin, который превращает ваши @Composable-функции в код, который Compose действительно может выполнять и эффективно рекомпоновать.

app/build.gradle.kts

/app/build.gradle.kts

Здесь настраивается сам модуль приложения: версии SDK, поведение сборки и все библиотечные зависимости.

Плагины и зависимости через каталог версий

Вместо того чтобы вручную писать id плагинов или Maven-координаты, этот файл берёт всё из gradle/libs.versions.toml через сгенерированный аксессор libs:

plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.compose)
}

dependencies {
    implementation(libs.androidx.core.ktx)
    implementation(libs.androidx.activity.compose)
    implementation(libs.androidx.material3)
    // ...
}
Частая ошибка: отсутствующий плагин ломает сборку. Все два плагина выше должны быть подключены вместе. Если alias(libs.plugins.kotlin.android) пропущен, у Gradle вообще нет настройки компиляции Kotlin для модуля — а плагин компилятора Compose, которому нужен уже подключённый плагин Kotlin Android, не сможет настроиться. Симптом — обычно ошибка синхронизации Gradle с упоминанием отсутствующего расширения kotlin или неудачи подключения плагина компилятора Compose. Если видите такое, в первую очередь проверьте этот блок plugins { }.

Опции компилятора Kotlin: современное расширение kotlin { }

Старый способ задать целевую JVM — блок kotlinOptions { jvmTarget = "…" }, вложенный в android { }. Этот API устарел; текущий подход настраивает отдельное расширение kotlin { } (доступное после подключения плагина Kotlin Android):

kotlin {
    compilerOptions {
        jvmTarget.set(org.jetbrains.kotlin.gradle.dsl.JvmTarget.JVM_21)
    }
}

Держите это в соответствии с compileOptions { sourceCompatibility / targetCompatibility } внутри android { } — оба должны указывать на одну и ту же версию Java.

Compose BOM

Compose поставляется как десятки отдельных библиотек (ui, material3, foundation, анимация и т. д.), которые все должны быть совместимы по версиям друг с другом. Вместо того чтобы прописывать версию в каждой строке, вы импортируете одну платформенную зависимость Bill of Materials (BOM) — саму по себе разрешаемую из каталога — и каждая другая строка implementation(...) Compose ниже неё автоматически разрешается в согласованную, протестированную версию:

val composeBom = platform(libs.androidx.compose.bom)
implementation(composeBom)
androidTestImplementation(composeBom)

implementation(libs.androidx.ui)
implementation(libs.androidx.material3)
Обратите внимание: ни libs.androidx.ui, ни libs.androidx.material3 не несут собственной версии в каталоге — её подставляет BOM во время сборки.
Частая ошибка: объявление BOM дважды. Легко получить вторую лишнюю строку ниже в блоке dependencies { } — например, implementation(platform(libs.androidx.compose.bom)), повторённую после строки val composeBom = … выше. Это не фатально (Gradle просто объединяет дублирующее ограничение), но это лишний груз и признак того, что файл нужно почистить. BOM следует один раз присвоить val и применить к каждой конфигурации (implementation, androidTestImplementation, …), которой он нужен — и никогда не вставлять второй раз инлайном.

settings.gradle.kts

/settings.gradle.kts

Объявляет имя всего проекта и то, какие модули в него входят (здесь только :app), а также то, из каких репозиториев Gradle разрешено скачивать зависимости и плагины (Google и Maven Central).

plugins {
    id("org.gradle.toolchains.foojay-resolver-convention") version "1.0.0"
}

Плагин Foojay Toolchains Resolver позволяет Gradle автоматически скачать подходящий JDK, если запрошенный в gradle/gradle-daemon-jvm.properties (см. ниже) ещё не установлен на вашей машине, вместо того чтобы падать со сборкой и просить установить его вручную.

gradle/gradle-daemon-jvm.properties

/gradle/gradle-daemon-jvm.properties

Сгенерированный задачей Gradle updateDaemonJvm, этот файл фиксирует точный JDK (toolchainVersion=21, вендор JETBRAINS), на котором работает сам демон Gradle, с URL для скачивания под каждую ОС/архитектуру. Он держит всех в команде — и CI — на идентичном JDK, автоматически разрешаемом через плагин Foojay выше, а не на том JDK, который случайно оказался в PATH каждой машины.

local.properties

/local.properties

Хранит конфигурацию, зависящую от машины — прежде всего sdk.dir, путь к вашей локальной установке Android SDK, который Android Studio записывает автоматически при первом открытии проекта.

Этот файл никогда не должен попадать в систему контроля версий. Путь к SDK специфичен для одной машины (sdk.dir=D:\AndroidSDK ничего не значит на Mac или Linux коллеги либо на CI) — именно поэтому стандартный шаблон Android .gitignore его исключает. Если вы обнаружите local.properties закоммиченным в репозиторий, добавьте его в .gitignore и удалите из системы контроля версий; оставленный там файл может перезаписать путь к SDK у коллеги при следующем pull.

AndroidManifest.xml

/app/src/main/AndroidManifest.xml

Даже приложению, полностью построенному на Compose, всё ещё нужен манифест — именно по нему Android узнаёт, что приложение существует, какова его точка входа и что ему разрешено делать. В этом учебнике он объявляет ровно одну <activity> — MainActivity, помеченную как launcher-activity через intent-фильтр MAIN/LAUNCHER, то есть экран, который открывается при нажатии пользователем на иконку приложения. Атрибуты android:icon и android:roundIcon указывают на ресурсы адаптивной иконки, описанные далее.

В полноценном приложении вы также перечислили бы здесь разрешения (камера, интернет, местоположение…) и любые дополнительные activity или сервисы. Этому учебнику ничего из этого не нужно.

Ресурсы иконки приложения

/app/src/main/res/drawable/, /app/src/main/res/mipmap-anydpi-v26/

Четыре небольших XML-ресурса определяют иконку приложения как адаптивную иконку — формат, который Android использует с API 26, состоящий из двух отдельных векторных слоёв, которые система компонует, маскирует (в круг, «сквиркл» и т. п.) и может анимировать независимо:

ФайлРоль
drawable/ic_launcher_background.xmlВекторный drawable для фонового слоя иконки (здесь — сплошной фиолетовый квадрат).
drawable/ic_launcher_foreground.xmlВекторный drawable для переднего слоя (здесь — простая фигура ромба).
mipmap-anydpi-v26/ic_launcher.xml<adaptive-icon>, ссылающийся на два drawable выше; именно в него разрешается android:icon="@mipmap/ic_launcher" в манифесте.
mipmap-anydpi-v26/ic_launcher_round.xmlТа же пара, разрешаемая для android:roundIcon в лаунчерах, предпочитающих круглую маску.
Квалификатор -v26 означает, что эти ресурсы адаптивной иконки применяются только на API 26+. Поскольку minSdk этого проекта — 24, устройства на API 24–25 откатываются к тем ресурсам ic_launcher/ic_launcher_round, которые есть в папках под конкретные плотности (mipmap-hdpi, mipmap-xhdpi, …). Если в этом проекте таких нет, добавьте обычные PNG/WebP-заглушки для этих двух уровней API или поднимите minSdk до 26, если поддержка этих версий не нужна.

MainActivity.kt

/app/src/main/java/com/example/composetutorial/MainActivity.kt

Единственная Activity, содержащая весь интерфейс — распространённый шаблон в приложениях на Compose, поскольку экраны компонуются и переключаются в Kotlin, а не через запуск новых Activity.

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            ComposeTutorialTheme {
                TutorialApp()
            }
        }
    }
}

setContent { … } — это мост между классическим миром Android Activity и Compose: всё, что внутри него, — это composable-код. Здесь нет ни XML-файла макета, ни R.layout.activity_main.

Ниже Activity находится TutorialApp() — composable, который фактически формирует макет экрана. Он оборачивает всё в Scaffold (структурный компонент Material, который резервирует место для верхней панели и корректно встраивает ваш контент с учётом отступов), а затем размещает четыре демонстрационных раздела — GreetingCard, CounterButton, ProfileForm, TaskList — внутри прокручиваемого Column.

SectionLabel("4. Lists with LazyColumn")
TaskList(
    modifier = Modifier
        .fillMaxWidth()
        .height(300.dp)
)
Почему TaskList получает явный .height(300.dp). Внешний Column уже прокручиваемый (.verticalScroll(rememberScrollState())), а TaskList сам по себе — прокручиваемый LazyColumn. Если дать TaskList неограниченный размер — например, обернуть его в Box(Modifier.fillMaxSize()) — это поместит один прокручиваемый контейнер с неограниченной высотой внутрь другого, что Compose не может измерить и что приводит к падению во время выполнения с IllegalStateException. Фиксированная (или иным образом ограниченная, например через Modifier.weight() в непрокручиваемом родителе) высота — это то, что делает ленивый список безопасным для вложения в прокручиваемый столбец.

Файлы ui/theme/

/app/src/main/java/com/example/composetutorial/ui/theme/

Три небольших файла, которые вместе определяют визуальную идентичность приложения через систему темизации Material 3.

Color.kt

Сырые константы Color(0x…) для светлой и тёмной палитры — просто значения, без логики.

Type.kt

Объект Typography, переопределяющий несколько именованных текстовых стилей Material 3 (bodyLarge, titleLarge, labelSmall) размерами и насыщенностью шрифта этого приложения.

Theme.kt

Определяет ComposeTutorialTheme — composable-обёртку, которую вы вызываете один раз в корне приложения. Она выбирает светлую или тёмную ColorScheme (учитывая системную настройку и даже «динамический цвет» на основе обоев на Android 12+), затем передаёт цвета и типографику в MaterialTheme из Compose:

MaterialTheme(
    colorScheme = colorScheme,
    typography = AppTypography,
    content = content
)

Теперь каждый composable внутри content может читать MaterialTheme.colorScheme.primary, MaterialTheme.typography.bodyLarge и т. д. вместо жёстко прописанных цветов и шрифтов.

Файлы components/

/app/src/main/java/com/example/composetutorial/components/

Четыре небольших, сфокусированных composable, каждый демонстрирует одну ключевую идею Compose. MainActivity.kt собирает все четыре в один экран.

GreetingCard.kt

Идея: composable без состояния (stateless). Он принимает параметр name и выдаёт Material Card с двумя строками текста — и ничего больше. Он не владеет состоянием и не имеет побочных эффектов, что делает его тривиально переиспользуемым и удобным для превью с разными входными данными.

CounterButton.kt

Идея: состояние и рекомпозиция. Хранит счётчик через remember { mutableIntStateOf(0) }. Нажатие кнопки увеличивает его; поскольку composable читает это состояние, Compose автоматически перезапускает (рекомпонует) только этот небольшой фрагмент интерфейса при каждом его изменении.

ProfileForm.kt

Идея: поднятие состояния (state hoisting). Текстовое поле, текущее значение которого хранится в remember { mutableStateOf("") } вне самого OutlinedTextField, а затем передаётся обратно через value / onValueChange. Текстовое поле не управляет своим состоянием — это делает вызывающий код — что является стандартным, тестируемым шаблоном для интерактивного интерфейса на Compose.

TaskList.kt

Идея: эффективные списки. Использует LazyColumn (аналог RecyclerView в Compose) на основе mutableStateListOf из небольшого data-класса Task, поэтому компонуются только элементы, видимые на экране в данный момент, а переключение чекбокса обновляет только эту строку.

Что такое Jetpack Compose

Jetpack Compose — это современный UI-инструментарий Google для Android, полностью написанный на Kotlin. Он заменяет старую систему View (XML-макеты + связующий код Activity/Fragment) декларативной моделью, заимствованной у таких фреймворков, как React и Flutter:

Классические View (императивно)Compose (декларативно)
Как вы строите UIXML-файлы макетов + код на Kotlin/Java, который мутирует viewФункции Kotlin, описывающие UI для текущего состояния
Обновление UIВы вручную вызываете setText(), setVisibility() и т. д.Вы меняете состояние; Compose автоматически перезапускает нужные функции
ПереиспользованиеПодклассы View, <include>Обычные функции Kotlin

Поскольку UI — это просто функция от состояния, большинство ошибок в Compose сводятся к гораздо более простой и знакомой проблеме: «правильно ли моё состояние?» — вместо «не забыл ли я обновить вот это конкретное view?».

Composable-функции

Composable-функция — это любая функция, помеченная аннотацией @Composable. Она описывает фрагмент UI, вызывая другие composable:

@Composable
fun GreetingCard(name: String, modifier: Modifier = Modifier) {
    Card(modifier = modifier) {
        Text("Hello, $name")
    }
}
  • Composable-функции можно вызывать только из других composable-функций (или из точки входа вроде setContent { }).
  • Они могут выполняться в любом порядке, параллельно и более одного раза — поэтому им следует избегать побочных эффектов и просто описывать UI исходя из своих входных данных.
  • По соглашению они принимают завершающий параметр modifier: Modifier = Modifier (см. Модификаторы), чтобы вызывающий код управлял макетом.

Состояние и рекомпозиция

Рекомпозиция — это процесс повторного выполнения composable-функций при изменении состояния, которое они читают, чтобы UI на экране оставался синхронизированным с состоянием приложения. Ключевой строительный блок — mutableStateOf:

var count by remember { mutableIntStateOf(0) }

Button(onClick = { count++ }) { Text("Tap me") }
Text("Clicked $count times")   // перезапускается при каждом изменении count
  • mutableStateOf (и специализированные mutableIntStateOf, mutableStateListOf и т. д.) создаёт наблюдаемое состояние — Compose отслеживает каждый composable, который его читает.
  • remember { … } кэширует это состояние между рекомпозициями одного и того же экземпляра composable — без него состояние сбрасывалось бы к начальному значению при каждом повторном запуске функции.
  • remember не переживает изменения конфигурации (например, поворот экрана) или смерть процесса — для этого нужно использовать rememberSaveable.
Умная рекомпозиция: Compose перезапускает только те composable, которые фактически читают изменённое состояние, а не весь экран — именно поэтому интерфейс остаётся быстрым даже в больших приложениях.

Модификаторы

Modifier — это цепочка инструкций, которые украшают или настраивают то, как composable измеряется, размещается, отрисовывается или реагирует на ввод — отступы, размер, обработка нажатий, цвет фона и многое другое:

Text(
    text = "Hello",
    modifier = Modifier
        .fillMaxWidth()
        .padding(16.dp)
        .background(Color.LightGray)
        .clickable { /* ... */ }
)

Порядок важен — каждый модификатор оборачивает результат предыдущего, поэтому padding().background() рисует фон снаружи отступа, а background().padding() — внутри. Именно поэтому каждый layout-компонент в этом проекте принимает необязательный параметр modifier: это позволяет родителю управлять отступами и размерами, не требуя от дочернего элемента знания о его контексте.

Макеты: Column, Row, Box

В Compose есть три фундаментальных layout-компонента, примерно соответствующих LinearLayout и FrameLayout в старой системе View:

ComposableРасполагает дочерние элементы…
Columnвертикально, сверху вниз
Rowгоризонтально, слева направо
Boxдруг на друге (для наложений, бейджей и т. п.)

Все три принимают параметры Arrangement (расстояние между дочерними элементами) и Alignment (выравнивание дочерних элементов по поперечной оси). MainActivity.kt использует Column с Arrangement.spacedBy(4.dp) для размещения разделов учебника, а строка в TaskList.kt использует Alignment.CenterVertically для выравнивания чекбокса с его подписью.

Списки: LazyColumn

Для списков, которые могут быть длинными или неограниченными, используйте LazyColumn (или LazyRow) вместо Column с циклом. «Lazy» означает, что он компонует и измеряет только те элементы, которые фактически видны на экране, переиспользуя composable по мере прокрутки пользователем — прямой аналог RecyclerView.

LazyColumn {
    items(tasks) { task ->
        TaskRow(task = task, onToggle = { /* ... */ })
    }
}
Использование обычного Column для большого или растущего списка компонует все элементы заранее, что тратит память и процессор. LazyColumn — правильный выбор по умолчанию, когда размер списка не мал и не фиксирован.

Компоненты Material 3

Библиотека androidx.compose.material3 предоставляет готовые, учитывающие тему UI-компоненты, реализующие спецификацию Google Material Design 3. В этом проекте используются:

КомпонентДля чего

TopAppBarПанель заголовка в верхней части экрана

Каждый из них автоматически подхватывает цвета из MaterialTheme.colorScheme и текстовые стили из MaterialTheme.typography — именно это и настраивает Theme.kt.

Темизация

Темизация в Compose течёт в одном направлении: вы задаёте её один раз, near the root (ComposeTutorialTheme { … } в MainActivity), и каждый composable ниже читает из неё через MaterialTheme.colorScheme / MaterialTheme.typography / MaterialTheme.shapes. Именно поэтому ни один из четырёх файлов компонентов не прописывает жёстко ни одного цвета или шрифта — все они полагаются на тему, так что переключение на тёмный режим или изменение стиля всего приложения означает редактирование Theme.kt и Color.kt в одном месте, а не поиск по каждому экрану.

Превью

Любой composable, помеченный @Preview, может быть отрисован панелью Design в Android Studio без сборки и запуска приложения — без эмулятора, без устройства, часто менее чем за секунду. Каждый файл в components/ заканчивается таким превью:

@Preview(showBackground = true)
@Composable
private fun GreetingCardPreview() {
    ComposeTutorialTheme {
        GreetingCard(name = "Jetpack Compose")
    }
}

Оборачивание превью в тему приложения (как показано выше) гарантирует, что оно будет выглядеть точно так же, как во время выполнения. Вы можете наложить несколько аннотаций @Preview на одну функцию, чтобы увидеть её в светлом/тёмном режиме, с разным масштабом шрифта или разными размерами устройств рядом.

  5. Добавьте второе @Preview(uiMode = android.content.res.Configuration.UI_MODE_NIGHT_YES) к компоненту, чтобы увидеть его превью в тёмном режиме.
